# 差分导出与离线还原方案

状态：本文保留 2026-10-29 的调研依据；0.2.0 已按此方向实施。生产格式、字段和实际参数以 `export-v2-format.md` 为准，完整导出也采用 V2 清单并直接保存完整事实与派生文件。本页的原型体积数字不替代生产版本的大记录验收结果。

## 结论

可以实现。建议增加默认的无损差分格式，并随包提供仅使用 Python 标准库的 `restore.py`。它还原的是已经采集、落盘的数据，不是执行用户操作或重放网页。完整数据导出继续可选。

差分的目标是让重复 DOM、重复快照和重复事件结构少占空间。不断新增且不可压缩的数据仍会使文件增长，不能承诺无限记录的文件大小保持固定。体积可近似理解为“基线 + 新增信息 + 差分与索引开销”。

## 现状与可节省部分

- `src/exporter.cjs` 将原始 `timeline.jsonl` 完整放入 ZIP，其中 `dom.snapshot.payload` 已包含 HTML、tree、forms、frames、shadowRoots 等。随后又为每个快照生成 HTML 和 state JSON。后两者是便于分析的派生副本。
- ZIP 使用 DEFLATE level 6，但不同 ZIP 条目的压缩字典彼此独立；快照副本及不同快照之间的重复内容仍占空间。
- `MutationObserver` 记录不能代替无损差分编码。增删子树在观察器回调时采样，暂停和导航存在观测边界，表单属性值也不能仅由 HTML 或 mutation 完整重建。应保留所有原始事件，直接对已保存字节做差分。
- 已有导出截点正确：`store.capture()` 在写入队列中取得元数据和时间线字节边界；导出过程只读取该边界。继续保留事件数校验、SHA-256、临时文件完成后原子替换的行为。

## 两个独立配置维度

| 配置 | 可选值 | 含义 |
| --- | --- | --- |
| 数据编码 | `delta` / `full` | 使用基线和差分，或保存完整文件 |
| ZIP 压缩 | `deflate` / `store` | 使用 DEFLATE，或关闭 ZIP 压缩 |

建议默认 `delta + deflate`；`full + deflate` 保持当前直接解压阅读的体验；`full + store` 满足完全关闭差分与 ZIP 压缩的要求。`delta + store` 也有明确含义：保留差分编码但不做通用压缩。界面可提供“差分导出 / 完整导出”和独立“ZIP 压缩”选项，不把两者混为同一个开关。

差分结果比完整数据更大时，自动将该块保存为完整块。这是编码器的正常回退，不删减数据。选定模式应写入 manifest。

## 推荐格式与还原契约

新增 `schemaVersion: 2`，与现有 V1 包明确区分。V1 继续可导出和阅读。建议物理结构：

```text
AGENT_README.md          先说明本包模式与恢复命令
manifest.json            格式、截点、编码参数、原始时间线长度与 SHA-256
session.json             会话元数据
restore.py               Python 标准库离线恢复工具
index.jsonl              按序排列的块、事件边界及检查点索引
objects/                 基线字节、差分命令与新增字节
```

恢复后的主要事实文件为原始 `timeline.jsonl`：必须与导出截点内的源文件**逐字节一致**，包括顺序、所有 payload、JSON 转义、换行与原始值。不能通过重新序列化 JSON 来声称字节一致。session 与其他直接保存的逻辑文件也逐文件核对字节数和 SHA-256。

快照 HTML/state 以及 timeline Markdown 是派生阅读材料。默认包可不物理保存这些完整副本，由恢复工具按需生成；这部分应在 manifest 标明 `derived`，其重新生成的哈希写入恢复报告，不能冒用旧 V1 文件哈希。Python 与 JavaScript 对数字、转义、缩进的 JSON 序列化可能不同，“解析后的内容一致”和“文件字节一致”必须区分。

若验收要求恢复后**每个旧 V1 派生文件也逐字节一致**，采用同一个通用字节编码器处理所有逻辑文件，将原始派生文件的基线/差分及预期哈希纳入 manifest。这样 Python 只执行字节 COPY/ADD，无需模拟 `JSON.stringify`，可以对每个文件做严格 SHA-256 对账。此模式仍不会保存每个派生文件的全量副本，但首次基线和差分指令有额外开销；本次数据表的最小体积数字不包含这项严格兼容开销。

推荐产品契约：原始时间线与会话文件保证字节一致；阅读材料保证完整内容等价，明确属于派生输出。保留 `full` 模式供需要原始 V1 文件布局的工作流使用。

## 算法选择

| 方案 | 特点 | 判断 |
| --- | --- | --- |
| 最长公共前缀/后缀 | 只有一次中间替换，实现最简单 | 时间戳、reason 和多处 DOM 变化分布在整条 JSON 中，本次样本几乎没有收益 |
| 多段字节 COPY/ADD | COPY 引用基线偏移和长度；ADD 携带新增字节，可保存任意内容 | 推荐，恢复逻辑小，易做严格字节校验；无需理解 DOM |
| JSON 结构差分 | 对对象/数组应用设置、删除、插入等操作 | 可读性好，但数组位移、对象键顺序、数值及转义使字节复原复杂，且需完整解析大对象；不作为第一版事实编码 |
| 直接重放 DOM mutations | 利用已经采集的 DOM 操作 | 无法保证原始数据或网页完整恢复，不采用 |

原型用 64-byte 基线块建立滚动指纹索引；匹配后逐字节比较以排除指纹碰撞，再输出 COPY/ADD。每条候选链限制 16 次差分，差分达到原长度的 95% 时保存完整数据。阈值是原型参数，正式版应按实际编码和压缩成本验证。

生产编码器应使用有界块，不能简单照搬原型的“整条事件放入内存”：

1. 按固定导出截点顺序读取原始时间线，用约 4 MiB 数据块承载字节流；块边界允许落在 UTF-8 字符或 JSON 事件内部，恢复时先拼回原字节再解析。
2. 使用有大小上限的基线窗口与匹配索引；跨块/跨快照引用需写明对象、偏移和长度。历史基线可落盘，不把所有 documentId 的快照永久留在内存。
3. 每约 64 MiB 原始数据或最多 16 层依赖建立独立检查点，取先到者。文档切换和差分效率低时也可写完整基线。检查点限制随机定位的恢复工作量，而不是限制可记录数据量。
4. `index.jsonl` 顺序写入，记录原始字节范围、seq 范围、依赖与校验值。超大单事件可以横跨多个块，不能因此截断 payload。
5. COPY 只引用已验证的合法字节范围；ADD 长度有明确上限。块最终长度和 SHA-256 必须与 manifest 一致。重复块可按内容哈希复用，但哈希相同仍应有一致长度和字节校验策略。
6. 编码器写临时结果，成功校验后提交；取消或失败保留旧目标 ZIP。对不可压缩数据回退到完整块。

块大小、窗口、检查点间隔和 ZIP64 支持需要在正式实现中用大数据验收。本次原型只验证差分算法与小样本恢复，未验证上述生产容器性能。

## 随包 Python 脚本

推荐 Python 3.10 或更新版本，使用 `zipfile`、`hashlib`、`json`、`struct`、`pathlib` 等标准库，无需 `pip install`、网络或 TraceDock 安装。将脚本和说明解出后，可直接读取其余 ZIP 内容：

```powershell
python .\restore.py .\recording.zip --output .\restored
```

也支持展开后的目录，便于 Agent 环境处理。脚本顺序恢复数据块，COPY 从有界缓存或已恢复的临时文件按偏移读取，ADD 流式写入；避免 `ZipFile.read()` 一次读入巨型条目。还原完成后再逐行生成派生快照和 Markdown，可提供 `--timeline-only` 以减少阅读材料的磁盘开销。

恢复工具应输出机器可读报告，包含输入格式、事件数量、各事实文件长度/哈希、派生文件哈希和成功状态。无法通过校验时退出非零，明确损坏对象和最后通过的检查点，不能静默跳过。输入对象路径必须限制在包内，输出路径限制在指定目录；未知操作码、越界 COPY、非法长度、循环/前向依赖均拒绝。默认拒绝覆盖已有恢复目录，避免半成品看起来像完整结果。

原始字节编码不会改变中文、emoji、NUL、CRLF、JSON 转义、空字符串或已落盘的孤立代理项转义。恢复派生内容时才解析 JSON；不得执行快照 HTML 或包内网页脚本。这里的“恢复”不增加原采集范围，也不补齐暂停、跨域 iframe 或未采集内容。

## 本次测量

原型与结果位于 `output/delta-research/measure.cjs` 和 `measurements.json`。运行命令：

```powershell
node output\delta-research\measure.cjs
```

原型保存了独立输入 ZIP 副本，SHA-256 为 `77e8ac99457da94553f243ac63546c402b67f5215acec4390f306fe8ec43a562`。所有算法结果均恢复并与原始时间线做 Buffer 字节比较和 SHA-256 对账；另验证 32 组空内容、中文、emoji、NUL、换行、插入、随机字节与重复字节组合。

下表都是**数据区 ZIP 大小（bytes）**，不含指南、manifest、索引扩展和恢复脚本的固定开销。为公平比较，“时间线 + 快照”在同一脚本中重建数据区，不能直接等同于完整交付 ZIP 的总大小。

| 样本 | 时间线 + 完整快照副本 | 仅时间线（去副本） | 去副本 + 快照块差分 | 合计减少 |
| --- | ---: | ---: | ---: | ---: |
| 实际预览会话，83 事件、2 快照 | 43,330 | 19,400 | 12,290 | 71.6% |
| 浏览器 smoke 交互前 62 事件、12 快照 | 157,816 | 56,089 | 22,096 | 86.0% |
| 完整 smoke，577 事件、13 快照 | 203,262 | 89,279 | 48,604 | 76.1% |

其中去副本本身分别减少约 55.2%、64.5%、56.1%；在此基础上，快照差分进一步减少约 36.6%、60.6%、45.6%。不能把合计收益全部归因于差分算法。

完整 smoke 包含为分页验收程序生成的 510 条键盘事件，所以另列，不作为真实大规模使用的压缩率承诺。将差分扩展到所有事件类型时，完整 smoke 数据区可降至 32,638 B，但其大量重复测试事件会显著放大收益；前 62 事件反而从快照差分的 22,096 B 增至 22,360 B。因此优先对重复快照编码，并对实际 ZIP 成本做回退判断，比一律差分所有事件更稳妥。

当前样本小于 3 MiB 时间线，原型故意完整读入样本以便比较；它不是生产恢复脚本，也没有证明 GB 级内存上限、吞吐或恢复时间。正式块容器、脚本、索引和严格 V1 派生文件兼容需要另外计入体积。

## 超大记录还需改造的路径

差分导出能缩小交付文件，但不能单独解决当前应用的大记录内存问题：

- `SessionStore.init()` 完整读取、拆分和解析每个会话；损坏尾部恢复还可能重新拼接完整内容。
- `_readEvents()` 为整条时间线分配 Buffer，再生成字符串、行数组和事件对象；每次分页、搜索和详情都会调用它。500 条分页只限制返回量。
- renderer 实时刷新约每 180ms 请求时间线；多页和详情会重复全量扫描。详情在完整 IPC/序列化之后才截显示长度。
- 导出目前逐行读取，但一个大快照仍会成为完整字符串与对象；文件清单、快照索引和校验表随记录增长。
- 主进程将整次导出放在控制命令队列中，长导出会让暂停/结束控制排队。

建议作为独立工作项：启动流式恢复计数；写入时建立 seq/type/byteOffset/length 索引；分页和详情按范围读；搜索顺序扫描；UI 增量获取摘要。差分编码放 worker，在确定一致截点后释放控制队列。导出索引和校验清单采用 JSONL 流式输出。当前采集器一次构建完整快照的上游内存成本也需独立衡量。

## 实施与验收顺序

1. 固定 V2 编码与恢复契约；实现有界字节块、COPY/ADD、完整块回退及独立检查点。
2. 接入两个配置维度；保留原始 V1 full 导出；沿用一致截点和原子提交。
3. 随包交付无依赖 Python 恢复脚本及针对该模式的 Agent 说明。
4. 验证所有事实文件字节一致、派生内容等价；覆盖 UTF-8 跨块、超大单事件、文档切换、坏哈希、坏偏移、截断包、取消、重复输出和导出期间继续录制。
5. 另做 GB 级实测：长时间微量变化、连续大页导航、巨大表单值、低重复内容、随机内容、超大单快照；记录实际最终 ZIP 大小、吞吐、峰值 RSS、暂存磁盘、随机定位与恢复耗时。
6. 与本地流式索引改造结合后，才声明支持超大记录的整套工作流。
